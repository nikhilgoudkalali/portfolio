Deep dives into what I built

The problem

Every routing decision went through a single shared switchagent tool whose description listed all sub-agents at once. Adding or removing a sub-agent meant editing that one shared config — fine for whoever wrote it, dangerous for anyone else, and it forced the LLM to reason over a large blob of text on every single call.

What I built

  • Each sub-agent's “when should I handle this?” description becomes a dedicated tool description, exposed as SwitchTo<agent_name> and attached to the parent at runtime.
  • When the parent LLM calls it, the response returns the agent name and the backend loads that sub-agent — control genuinely shifts, it's not a prompt trick.
  • Every sub-agent automatically receives a switchAgent tool that knows its parent, so out-of-scope questions hand control back up.
  • Multi-level parent/child hierarchies fall out of the same mechanism.
  • Routing stays purely LLM judgement on the tool description — no keyword matching or confidence scoring layered on top.
Why it mattered

Maintainability first, speed second.

  • Before: one shared tool, manual edits, large description on every call.
  • After: per-agent tools generated at runtime — add or remove an agent without touching shared config.
  • Observed effect: routing roughly ~30% faster, because each call now reasons over a small focused description. Observed before/after, not a formal benchmark — the maintainability fix was the actual driver.

Agent governance lifecycle · version cloning · scheduled validity windows

An AI agent that a user is still configuring must never be the same agent the business runs in production. I built the versioning and validity system that guarantees every agent passes a controlled lifecycle — draft, approval, activation on a date, automatic retirement on a date — before any other module is allowed to use it.

Lifecycle

  1. DRAFT Default on creation — connect tools, test, validate and modify freely.
  2. →
  3. WAITING_FOR_APPROVAL Author is satisfied it works, submits it for review.
  4. →
  5. APPROVED Team Lead / Manager reviews, adds a remark plus start and end dates.
  6. →
  7. ACTIVE Immediately, or automatically on a future start date. Other modules can now run it.
  8. →
  9. RETIRED Set automatically once the end date is reached.

REJECTED — the lead can send an agent back if it doesn't meet requirements; the author keeps editing the draft and resubmits. And the activation logic is date-aware: if the approved start date is today the agent goes straight APPROVED → ACTIVE; if it's a future date it sits at APPROVED and flips to ACTIVE by itself on that day.

Versioning rules I implemented

  • Every agent starts at Version 1, and users can assign their own labels (Alpha, Beta, …).
  • An ACTIVE agent can never be modified directly — the live version is immutable by design.
  • To change it, the user clicks “New Draft Agent” and the system creates a DRAFT_VERSION — a copy of the active agent, which becomes Version 2.
  • The draft → approval → active cycle then repeats for that new version, so the live agent is never disrupted.
  • On activation of the new version, Version 1 automatically moves to RETIRED.
  • Only once ACTIVE can other modules of the product use or run the agent.

Why it matters

  • Clean audit trail across versions — what changed, who approved it, and when it was valid.
  • Only validated, approved agents ever run in production.
  • Safe iteration: draft, test and iterate freely without touching the live agent.
  • Validity control — start and end dates mean an agent only runs inside its intended window (campaign agents, seasonal assistants, time-boxed proofs of concept).
  • Governance via Team Lead / Senior approval, which matters most on the hop from local testing to production.
Design decisions worth discussing
  • Copy-on-draft, not edit-in-place: cloning means the active version can never be corrupted by a half-finished edit.
  • Scheduled activation instead of a manual go-live step — the flip is driven by the approved start date, so it happens without someone remembering to press a button.
  • Automatic retirement on the end date keeps stale agents from being invoked by other modules.
  • The approver's remark is stored with the version, so a rejection always explains what to fix.

The problem

An agent with 100 connected tools shipped all 100 tool definitions to the LLM on every call. That is expensive in tokens and — worse — it degrades selection accuracy. A model choosing 1 correct tool out of 100 gets noticeably “confused”.

Indexing — once per sub-agent

  1. Read the user's routing description (“when should the main agent hand off to this agent?”).
  2. Trigger an autonomous agent that generates ~50 realistic questions a user might ask that should route here.
  3. Description + generated questions become one document per tool.
  4. Embed that document with a Llama-based embedding model and persist it to a vector store.
  5. If the user later edits the description, they can review and edit the generated questions too.

Query time

The live question is embedded and similarity-searched against the vector store. Only the top 5 tools (configurable via application properties) are sent to the LLM — not all 100.

The extra feature I added

Some tools must always be visible regardless of similarity — critical or global ones. I built an “exclude from RAG” toggle so selected tools bypass filtering entirely and are always included alongside the top-5 results.

Impact & honesty
  • Token cost per call drops sharply, because context shrinks from 100 tool schemas to 5.
  • Tool selection accuracy improves because the model is no longer choosing from noise.
  • No formal benchmark — a clear observed improvement, described as before/after.
  • Same lazy-loading philosophy as the skills system: load only what's relevant, at runtime.

What it solves

An agent that forgets everything between sessions feels broken, and sending full raw history every time is both slow and expensive. My long-term memory layer summarizes instead of replaying.

How it works

  • Pull the user's last 5 previous conversations.
  • Generate a clear summary of them.
  • Append that summary into the current prompt so the agent has continuity across sessions.

Where the boundary is

This is deliberately separate from the platform's session memory, which a teammate built: raw ordered message history (user / assistant / tool-call / tool-result) held in-process via a SessionMemoryAdvisor keyed on conversationId + userId, with older messages compressed once a size threshold is hit. I integrate with it directly — handoffs and splits call getMessagesFromMemory / addDataInChatMemory / deleteDataFromMemory — and its known limitation is real: in-process storage means a restart or a scale-out fragments session state, and Redis is the natural fix.

Design trade-off

Summary, not transcript.

  • Cheap, bounded prompt growth regardless of how long the user has been talking.
  • Adds one summarisation call — latency accepted for continuity.
  • Falls back gracefully when a user has fewer than 5 past conversations.

The problem

Other teams embed our agent widget inside their own product modules. Those modules hold context the agent needs — a moduleId, an auth token, the current record — but a prompt is written once and reused everywhere.

What I built

  • The embedding module passes custom parameters at invocation time.
  • Those values are injected into the prompt using {variableName} placeholder syntax.
  • Tool behaviour and instructions adapt to the embedding context automatically.

Example

A module passes moduleId when a user opens the agent from a specific list or page. The value is substituted into {moduleId} inside the prompt, so the agent fetches and renders data for exactly that context instead of asking the user where they meant.

Why it matters
  • One prompt serves many host products — no forked prompt copies.
  • Context-sensitive behaviour without recompiling or redeploying the agent.
  • Turns the agent widget into a reusable embeddable component for other teams.
